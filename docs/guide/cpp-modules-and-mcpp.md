# C++20/23 Modules and mcpp: Six Platforms

HuxerUI written as modules and built by mcpp: `import huxerui;` in place of the headers, one manifest in place of a CMake project, and Linux, Windows, macOS, iOS, Android and the Web as rows of that manifest.
This page is the path for three kinds of work — an application, a library for the HuxerUI ecosystem, and the SDK itself — from environment to distribution.
By default the result is the program the CMake build produces; what mcpp adds beyond that is optional and listed under [Build and development enhancements](#build-and-development-enhancements).
[`mcpp/README.md`](../../mcpp/README.md) has the repository details and [the design record](../design/mcpp-build-system.md) the reasons.

## Modules

```cpp
export module app;

import std;
import huxerui;
import app.resources;

using namespace huxerui;

[[huxerui::composable]]
View Counter() {
  auto count = UseState(0);
  return Row { Button("Count").OnClick([count] { count += 1; }), Text(count) };
}
```

`import huxerui;` names what `#include <huxerui/huxerui.h>` names and `import std;` replaces the standard headers, so a project contains no `#include`: pages are module units that reach each other by `import`, with no header to keep in step and no source list in the manifest.
`[[huxerui::composable]]`, `View` and `UseState` are the API the CMake path uses, transformed by the same `hcg`; `import app.resources;` is generated by hrc from `resources/`, with the declarations of the header the CMake path generates.
[C++20/23 modules and mcpp](../../skills/huxerui-app-development/references/cpp-modules-and-mcpp.md) has the rules that follow from modules: why `import std;` is required, why the entry stays empty, and what replaces a macro.

## Environment

One tool. [xlings](https://github.com/d2learn/xlings) installs [mcpp](https://github.com/mcpp-community/mcpp); mcpp installs everything else on first use: compilers, the GTK stack on Linux, the NDK, emsdk, the JDK, simulator tools, packaging tools.

```bash
xlings install mcpp -y --use
mcpp --version            # 2026.9.14.3 or newer
mcpp self doctor          # what is missing
```

iOS additionally needs Xcode on a Mac, because Apple's SDK is located rather than installed.
Before the first macOS or iOS build, install LLVM 22.1.8 once (`mcpp toolchain install llvm 22.1.8`); see [Known differences](#known-differences).
Nothing else is required on `PATH`.

`mcpp self doctor` is the diagnosis. In an mcpp project `huxerui doctor` reports whether `mcpp` is found and whether the requested platforms are enabled, then points at `mcpp self doctor` rather than running it: inside a package that command resolves the build, which can install a toolchain, and `huxerui doctor` changes nothing.

## An application

```bash
huxerui create app hello --build mcpp    # or: mcpp new hello --template huxerui.huxerui
cd hello
huxerui build && huxerui run              # or: mcpp build && mcpp run
```

The project is a manifest, a one-line build program and module units. No headers, no platform shells:

```
hello/
  mcpp.toml        huxerui.huxerui = "…", platforms = [linux, windows, macos, ios, android, emscripten]
  build.mcpp       huxerui::rules::configure({.resources = "resources"})
  src/main.cpp     the entry, outside the module graph
  src/app.cppm     export module app; import std; import huxerui; import app.resources;
  resources/       raw/, images/ … reachable as app::resources::…
  windows/installer/  the interface the Windows Setup.exe runs: a package of its own
```

The CLI's verbs are the ones a CMake project uses, and in an mcpp project they run mcpp:

| `huxerui` | runs |
|---|---|
| `build <platform>` | `mcpp build --target <row>` |
| `run <platform> [--device <id>]` | `mcpp run --target <row>`, with `--format app` on macOS and iOS and `--format apk` on Android; the device reaches `adb-run` as `ANDROID_SERIAL` and `simctl-run` as `SIMCTL_RUN_UDID` |
| `package <platform>` | `mcpp pack --target <row> --format <format>`: the artifact CMake's `huxerui package` produces ([Distribution](#distribution)) |
| `platform add <platform>` | adds the row to `[package] platforms` |
| `--profile release` | `--release` |

`--generator`, `--java-home` and `--source` are refused, because the toolchain, the JDK and the HuxerUI dependency are mcpp's, a payload's and the manifest's.

## Six platforms

Another platform is another row of the same manifest:

```bash
mcpp build --target wasm32-emscripten
mcpp build --target x86_64-linux-android
mcpp build --target aarch64-ios-sim         # on macOS
```

The default program on every row is the one the CMake build produces:

- **Linking.** The framework is linked statically into the application on Linux, Windows, macOS, iOS and the Web, and is its own `libhuxerui.so` on Android, loaded by name from the Java host, as the Gradle build sets `HUXERUI_BUILD_SHARED=ON`. That is the framework's own statement, per row in its manifest (`[target.'cfg(env = "android")'.targets.huxerui] kind = "shared"`), so an application writes one dependency line and chooses nothing; a `linkage = "static"` against it on Android is reported and ignored.
- **Platform floors.** Android API 23, iOS 15.0, macOS 12.0. The template states them, and the framework refuses a lower value before anything compiles.
- **Resources.** Where the CMake shells put them: `<executable>.resources/` beside the program, `Contents/Resources/HuxerUI` in a macOS bundle, the root of an iOS bundle, `assets/` in an APK, the preloaded file system on the Web.
- **Profiling.** Compile-time profiling is the `profiling` feature, off by default, as the SDK a CMake application builds against carries none.

## Distribution

`huxerui package <platform>` produces what it produces under CMake:

| Platform | `--target` | `huxerui package` runs `mcpp pack --format` | `mcpp run --format` hands it to |
|---|---|---|---|
| Windows | `x86_64-windows-msvc` | `setup`: `<name>-Setup-<version>.exe` | — |
| Linux | `x86_64-linux-gnu` | `appimage` | — |
| macOS | `aarch64-macos` | `dmg` | `macapp-run` (the `app` bundle, as `huxerui run macos` runs it) |
| iOS simulator | `aarch64-ios-sim` | `app` | `simctl-run` |
| Android | `x86_64-linux-android`, `aarch64-linux-android` | `apk`: one APK for both rows, the ABIs the Gradle template builds | `adb-run` |
| Web | `wasm32-emscripten` | `web`: a static directory | any static HTTP server |

```bash
huxerui package android     # mcpp pack --target aarch64-linux-android --target x86_64-linux-android --format apk
huxerui package windows     # mcpp pack --target x86_64-windows-msvc --format setup: hello-Setup-0.1.0.exe
```

The Windows Setup.exe is the one `huxerui package windows` produces under CMake: a Burn bundle whose interface is the project's own installer program in `windows/installer`. The page and the strings are those of the SDK's Windows template until the package carries a `src/app.cpp` or a `resources/` of its own.

The APK is debug-signed, carries a launcher icon (the application's `android/res`, or the SDK's), names the application by the project id `huxerui create --id` recorded, and takes `versionName` / `versionCode` from `[package] version`.

## A library for the ecosystem

[Lib-Live2D](https://github.com/HuxerUI/Lib-Live2D) is the worked example: a Live2D model on every row through one dependency line, and nothing about Cubism in the application.

```
live2d/
  mcpp.toml            [package] name = "live2d", namespace = "huxerui", platforms = […]
                       [dependencies] huxerui.huxerui = { git = "…", rev = "…" }
                       [lib] path = "modules/live2d.cppm"
  build.mcpp           huxerui::rules::configure({…}) selects the sources; mcpp::deploy() ships the shaders
  modules/live2d.cppm  export module huxerui.live2d; import huxerui;
  mcpp/cubism/         a path package wrapping the vendor SDK, one xim payload per platform
  examples/preview/    an application that imports the library: its own smoke test on every row
```

Three habits keep a library simple.
It calls the same `configure()` an application does and lets the rule select its sources.
It declares per-platform payloads in `[target.'cfg(…)'.xlings.workspace]` and reaches them with `mcpp::xpkg_dir`.
It deploys only what the application would not: `mcpp::deploy` reaches the consumer's staged tree, so a shader directory ships with every application that imports the library.

It names the framework `huxerui.huxerui`, the identity applications use, with no `linkage`: the framework states its own form per row, and a second name for the same package would provide `huxerui` twice.
A consumer writes `huxerui.live2d = { git = "…", rev = "…" }` and `import huxerui.live2d;`.
Distribution is the source: a git revision today, an index entry when published.

## The SDK

```bash
git clone https://github.com/HuxerUI/HuxerUI && cd HuxerUI
mcpp build                                    # the framework, this host
for s in unit runtime ui smoke; do (cd mcpp/huxerui-tests/$s && mcpp test); done   # CMake's suites
mcpp build --target x86_64-linux-android      # any row
cd mcpp/examples/01-import && mcpp pack --target x86_64-linux-android --format apk
```

`mcpp/` holds the rule packages the framework and every application share: `huxerui-build-rules` (what to compile, hcg, hrc), `huxerui-build-rules-gtk` (the Linux payload table, declared once) and `huxerui-build-rules-dist` (the distribution formats, through `mcpp:plugins`).
CMake remains the other build system, untouched; CI's parity job checks that the two describe the same sources, and [`mcpp/README.md`](../../mcpp/README.md) says what to touch when adding a file or a platform.

## Build and development enhancements

What mcpp offers beyond the CMake build. None of it changes the default program above; each is used through mcpp directly or through the manifest, not through the `huxerui` CLI.

- **Modules all the way.** No header in an application, and its resources are a module too (`import app.resources;`).
- **A provisioned environment.** Compilers, the GTK stack, the NDK, emsdk, the JDK, simulator tools and WiX are pinned by manifests and installed on first use rather than taken from system packages; `mcpp self doctor` diagnoses them.
- **One manifest, six rows.** `--target` selects the platform; there is no Gradle project, Xcode project or platform shell to keep in step.
- **More formats.** `mcpp pack --format msi` (the MSI the Setup.exe chains), `app` (the macOS bundle the DMG carries), `aab` (an Android App Bundle) and `tar` or `dir` (an archive or a directory of the staged program); several `--target` rows packed as one APK; `mcpp pack` at the SDK root packs the library itself for mcpp consumers ([`mcpp/README.md`](../../mcpp/README.md#packaging)).
- **Running on a device.** `mcpp run --target <row> --format apk|app` installs the package on an emulator, a simulator or a device and launches it; on macOS the bundle runs in the foreground.
- **Tests.** `mcpp test` builds and runs every `tests/**/*.cpp` as its own program; the SDK's suites are packages under `mcpp/huxerui-tests`.
- **Toolchains and dependencies.** `--toolchain` on `build`, `run`, `test` and `pack`; `mcpp why toolchain|runtime|deps|runners`; `mcpp.lock` with `--locked` and `--offline`; `--strict`, which turns the manifest's schema warnings into errors.
- **Linking shapes.** A shared framework on the desktop rows is one key on the dependency line, `huxerui.huxerui = { …, linkage = "shared" }`; an explicitly static framework on Android waits for [mcpp#642](https://github.com/mcpp-community/mcpp/issues/642).
- **Features.** `huxerui.huxerui = { version = "…", features = ["profiling"] }` turns compile-time profiling on.
- **A programmable build.** `build.mcpp` is C++. Rule packages such as `huxerui.rules` and the official `mcpp:plugins` extend it; `rules-metal`, for example, recompiles a Metal shader when a header it includes changes.

## Known differences

Where the mcpp build is not the CMake build, and why:

- **The application graph's standard.** Applications are c++23 while the framework and its tests are C++20. On macOS and iOS an application compiles its own C++ standard library (`llvm.libcxx`, declared in the template) for the platform floors; its sources need C++23, and a module graph has one standard ([mcpp#641](https://github.com/mcpp-community/mcpp/issues/641), item 2). A home without any LLVM resolves that package's compiler requirement to a version that does not exist, hence the LLVM 22.1.8 installation above (mcpp#641, item 1).
- **When the installer interface is built.** Every Windows build of an application builds `windows/installer` as a host tool, once per source and toolchain; CMake builds it only for a package build, but `mcpp pack` takes no features a narrower declaration could depend on (mcpp#641, item 4).
- **A shared macOS framework.** The optional shared form currently needs macOS 14.0 (mcpp#641, item 5); the default static form keeps 12.0.
